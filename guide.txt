Подключение ChatGPT к Obsidian
Полная инструкция по безопасному MCP прокси на Windows
Результат настройки: ChatGPT входит через Auth0 и обращается к локальному Obsidian через постоянный HTTPS адрес ngrok. Плагин возвращает инструменты, а реальный запрос списка корня успешно выполнен.
Документ объединяет пошаговый маршрут, все 25 доступных скриншотов этой настройки и исходного обсуждения, разбор ошибок, эксплуатацию, восстановление и техническое приложение с кодом.
Секреты на изображениях необратимо закрашены. Почта, домены и идентификаторы аккаунтов тоже скрыты. В тексте вместо личных значений используются шаблоны YOUR_NGROK_DOMAIN, YOUR_AUTH0_DOMAIN, YOUR_CLIENT_ID и YOUR_USER_ID.
Версия инструкции 8 октября 2026 года. Интерфейсы сервисов и бесплатные квоты могут изменяться. Ориентируйтесь на смысл настроек и официальные ссылки в конце.
Автор и адресат: инструкция подготовлена Codex для владельца личного хранилища Obsidian. Пароли и реальные ключи в документ не включены.

Как пользоваться инструкцией
1. Прочитайте схему и ограничения. Если подключение уже работает, начните с разделов Ежедневная работа и Проверка после перезагрузки.
2. Для повторной установки сначала подготовьте Obsidian и Node.js, затем аккаунты ngrok и Auth0. Используйте экранные шаги в том же порядке.
3. Настройте локальные файлы и сохраните секреты только на ПК. Лишь затем публикуйте прокси и подключайте MCP в ChatGPT.
4. Проверьте tools/list и реальный вызов. Не считайте одну зелёную надпись об аккаунте доказательством работоспособности всех инструментов.
5. При сбое используйте таблицу диагностики. Известная ошибка PowerShell уже исправлена в приведённых исходниках.
В Word используйте панель навигации по заголовкам. Снимки сохранены в исходном разрешении после закрашивания; их можно увеличить для просмотра мелких деталей.
Часть иллюстраций показывает промежуточные ошибки и дублирующиеся экраны. Они сохранены полностью по истории настройки и снабжены пояснением, какие действия действительно привели к результату.

Архитектура и границы доступа
Поток запроса: ChatGPT → публичный HTTPS адрес ngrok → HTTP 127.0.0.1:8787 → HTTPS 127.0.0.1:27124/mcp/ → открытое хранилище Obsidian.
Auth0 отвечает за вход пользователя и выдачу OAuth access token. Прокси проверяет подпись RS256, issuer, audience, exp, nbf при наличии, scope obsidian:mcp, User ID и Client ID. После проверки прокси подставляет свой локальный Bearer API ключ Obsidian.
Ключ Obsidian не передаётся ChatGPT и Auth0. Client Secret Auth0 не нужен прокси. Токен ngrok используется только клиентом туннеля. Эти три секрета нельзя менять местами.
Прокси слушает только loopback. Он пропускает маршруты /mcp и /mcp/, методы POST, GET и DELETE, а публично отдаёт только OAuth resource metadata. REST маршруты /vault/ наружу не публикуются.
Проверка сертификата Obsidian включена через локальную CA плагина. Итоговая реализация не использует постоянное отключение TLS проверки или noTLSVerify.
SSE ответы передаются потоком без буферизации целого ответа. Сохраняются MCP Session ID, Protocol Version и Last Event ID. Запросы ограничены 2 МБ, число одновременных запросов 16, общий лимит 300 запросов в минуту.
Разрешение obsidian:mcp даёт доступ к инструментам плагина, включая запись, удаление и выполнение команд. Это не read only прокси. Подтверждения опасных действий в ChatGPT остаются важной частью работы.

Выбор адреса и необходимые условия
Cloudflare Quick Tunnel даёт временный адрес trycloudflare.com и не поддерживает SSE. Для этой постоянной потоковой схемы он не подходит.
Cloudflare named tunnel можно использовать со своим доменом и маршрутом на 127.0.0.1:8787. Уже работающий tunnel без публичного маршрута сам по себе адрес для ChatGPT не создаёт. В этой настройке своего домена не было, поэтому выбран ngrok.
Бесплатный ngrok предоставляет закреплённый Dev Domain. Он сохраняется после перезапуска, но тариф имеет квоты трафика и запросов. Не считайте бесплатный тариф обещанием неограниченной доступности; проверяйте Usage в панели.
Нужны Windows, установленный Node.js версии 24 или новее, ngrok, работающий Obsidian и плагин Local REST API with MCP. В проверенной установке использовались Node.js 24.18.0, ngrok 3.39.9 и плагин 5.4.0.
Windows должна быть включена без сна. Задание запускается после входа текущего пользователя, не до входа на экране блокировки после перезагрузки. Блокировка уже открытой сессии отличается от выхода из неё.
Obsidian Sync с iPhone работает отдельно от MCP. Прокси читает Windows хранилище, а не iPhone напрямую. Дождитесь завершения Sync перед запросом свежих изменений; не редактируйте один файл одновременно на разных устройствах.
ngrok завершает публичный TLS на своей стороне и передаёт данные через туннель. Провайдер участвует в обработке трафика. Секреты нельзя класть в URL, переписку, журнал запросов или синхронизируемое хранилище.

Поля которые нужно подготовить
YOUR_NGROK_DOMAIN — назначенный ngrok домен без пути. PUBLIC_ORIGIN — https://YOUR_NGROK_DOMAIN. MCP URL и audience — https://YOUR_NGROK_DOMAIN/mcp/.
YOUR_AUTH0_DOMAIN — полный Domain tenant, например dev-example.us.auth0.com. Issuer — https://YOUR_AUTH0_DOMAIN/ с завершающим слешем. Регион копируется из панели, а не угадывается.
YOUR_CLIENT_ID — публичный идентификатор приложения ChatGPT Obsidian. YOUR_USER_ID — полный идентификатор пользователя tenant, включая префикс auth0|. Эти значения не являются паролями, но в данной копии документа скрыты.
Client Secret Auth0 — секрет приложения. Скопируйте его только в OAuth поле ChatGPT. Не отправляйте в чат и не сохраняйте в config.json прокси.
Obsidian API Key — секрет из настроек плагина. Установщик импортирует его из локального data.json. Исходная копия в настройках Obsidian остаётся под управлением самого плагина.
ngrok Authtoken — секрет аккаунта туннеля. Установщик запрашивает его через скрытый локальный ввод. В конфигурации ngrok.yml токен не хранится; при запуске он передаётся только дочернему процессу через его окружение.
Пароль пользователя Auth0 — отдельный пароль для входа в Universal Login. Почта не обязана совпадать с Obsidian или ChatGPT. Учётная запись панели Auth0 и пользователь внутри tenant — разные сущности.

Шаг 1 Первый ввод ключа Obsidian
Исторический скриншот из исходной беседы содержал открытый API ключ. Изображение включено с полностью закрытой областью команды и ввода. Так делать не нужно: секрет не должен быть текстом приглашения Read-Host, аргументом команды или сообщением в чате.
Правильный способ в итоговой установке: API ключ читается из локальной конфигурации плагина и сохраняется через Windows DPAPI. Токен ngrok вводится локально через Read-Host -AsSecureString. Если секрет уже стал доступен посторонним, его следует заменить у соответствующего сервиса.

Шаг 2 Первичная проверка локального сервера
Это ранняя проверка корневого адреса https://127.0.0.1:27124/. Ответ 200 подтверждает доступность локального сервера, но не проверяет работу MCP, OAuth или доступа из ChatGPT.
Для MCP нужен путь /mcp/. В исходной настройке GET без ключа возвращал 401, а запрос с ключом до initialize возвращал Server not initialized. Это не основание отключать авторизацию. В итоговой проверке использовались initialize, notifications/initialized и tools/list.

Шаг 3 Панель ngrok и постоянный домен
Зарегистрируйтесь в ngrok и выберите Free. В левом меню Gateway откройте Network → Domains. Скопируйте назначенный Dev Domain. Это адрес вида YOUR-NGROK-DOMAIN.ngrok-free.dev; возможны другие окончания, поэтому копируйте значение из своей панели.
Не создавайте туннель прямо на порт 27124. В этой схеме ngrok направляет трафик только на защищённый прокси http://127.0.0.1:8787. Ваш Authtoken находится в Your Authtoken; он потребуется локальному установщику, но не ChatGPT.

Шаг 5 Создание API Obsidian MCP
Откройте Applications → APIs → Create API. Name: Obsidian MCP. Identifier: https://YOUR-NGROK-DOMAIN.ngrok-free.dev/mcp/. Signing Algorithm: RS256. Сохраните завершающий слеш: Identifier, поле audience в прокси и resource в метаданных должны совпадать.
В Permissions добавьте obsidian:mcp с описанием Access my Obsidian vault through MCP. В Tenant Settings → Advanced включите Resource Parameter Compatibility Profile. Это позволяет Auth0 обрабатывать resource из MCP запроса как идентификатор нужного API.

Шаг 6 Политика доступа API

Шаг 7 Приложение ChatGPT Obsidian
Applications → Applications → Create Application. Имя: ChatGPT Obsidian. Тип: Regular Web Applications. Откройте Settings. Client ID нужен прокси и ChatGPT. Client Secret вводится только в защищённое поле OAuth настроек ChatGPT; локальному прокси этот секрет не нужен.

В этой настройке использовался https://chatgpt.com/connector_platform_oauth_redirect. При другом адресе в интерфейсе ChatGPT используйте именно его. Сохраните изменения.

Шаг 12 Итоговые типы OAuth входа
Итоговый экран: включены только Authorization Code и Refresh Token. Это соответствует входу пользователя и последующему обновлению access token.

Шаг 17 Ошибка обнаружения инструментов
Authentication succeeded, action discovery failed означает: этап входа прошёл, но список инструментов загрузить не удалось. Не заменяйте наугад ключи и не открывайте API без авторизации.
Нужно проверить requests.log: дошёл ли запрос с авторизацией, прошла ли проверка токена, есть ли initialize и tools/list, какой статус вернул Obsidian. Именно по журналу в этой настройке была найдена ошибка передачи сертификата из PowerShell.

Установка локального комплекта
Рабочий комплект сохранён в outputs/obsidian-mcp-proxy в папке этой задачи Codex. Для переноса скопируйте всю папку проекта в постоянное место, например C:\ObsidianMcpProxy. Не переносите её в Obsidian Sync и не переименовывайте после регистрации задания без обновления задания.
Комплект содержит config.json, proxy.mjs, start.mjs, Run.ps1, Install.ps1, Setup.cmd, package.json, package-lock.json и тесты. node_modules можно восстановить по lock файлу командой npm ci --ignore-scripts.
Установите ngrok официальным способом: winget install ngrok --source msstore. Проверьте node --version и ngrok version. В исходной настройке пакет из обычного источника winget оказался устаревшим; использована версия Microsoft Store.
Заполните config.json вашими публичными адресами, Client ID и User ID. Укажите port 8787 и scope obsidian:mcp. Если обязательное поле отсутствует, прокси должен отказаться запускаться.
В Install.ps1 проверьте путь PluginData до .obsidian/plugins/obsidian-local-rest-api/data.json нужного хранилища. В runtime.json после установки хранится путь к Obsidian. В техническом приложении личные пути заменены шаблонами, их надо заменить перед повторной установкой.
Запустите Setup.cmd двойным щелчком из Проводника под тем пользователем Windows, который будет постоянно работать с Obsidian. Введите Authtoken только в локальное скрытое приглашение и нажмите Enter. Он не выводится на экран и не попадает в аргументы команды.
Установщик импортирует ключ и CA сертификат Obsidian, создаёт защищённое состояние, регистрирует задачу ObsidianMcpProxy и запускает её. Права администратора в самой задаче не запрашиваются. Если регистрация блокируется политикой Windows, сначала решите этот вопрос локально.

Секреты автозапуск и файлы состояния
Каталог состояния: %LOCALAPPDATA%\ObsidianMcpProxy. Доступ к нему ограничивается текущим пользователем Windows и SYSTEM. secrets.dpapi.json содержит зашифрованные DPAPI значения; obsidian-ca.pem — открытый CA сертификат; runtime.json — пути программ; ngrok.yml — параметры туннеля.
DPAPI привязывает секреты к профилю Windows. Простое копирование secrets.dpapi.json на другой ПК или под другого пользователя не гарантирует расшифровку. После переноса выполните Install.ps1 заново и введите Authtoken локально.
DPAPI не защищает от уже работающего вредоносного процесса с правами этого же пользователя. Не передавайте каталог состояния другим людям. Публичный CA сертификат сам по себе не является закрытым ключом; CA private key в комплект не копируется.
Задача ObsidianMcpProxy запускает Run.ps1 при входе пользователя. Он открывает Obsidian при необходимости, запускает Node прокси, проверяет локальный 401 с правильным WWW-Authenticate и только затем запускает ngrok.
При завершении дочернего процесса supervisor пытается перезапустить связку через 30 секунд. При ошибках запуска статус записывается в status.log. Доступность процесса ngrok ещё не доказывает доступность публичного адреса — её проверяют отдельно.
requests.log содержит только время, метод, категорию маршрута, наличие авторизации, класс ошибки, MCP метод и HTTP статусы. Токены, почта, User ID, содержимое заметок и аргументы tools/call не записываются. Ротация ограничивает размер журнала.
Входящий запрос к /mcp/ без токена должен получить 401, а метаданные OAuth — 200. Это нормальное поведение. Нельзя публиковать порт Obsidian 27124 напрямую ради устранения 401.

Проверки после установки
Локально: убедитесь, что Obsidian открыт с нужным хранилищем, порт 27124 слушает 127.0.0.1 и прокси слушает 127.0.0.1:8787. Адрес 0.0.0.0 для этих сервисов в этой схеме не требуется.
Снаружи: GET https://YOUR_NGROK_DOMAIN/mcp/ без токена возвращает 401 и WWW-Authenticate с URL resource metadata. GET /.well-known/oauth-protected-resource/mcp/ возвращает resource и authorization_servers, совпадающие с конфигурацией.
При подключении ChatGPT: сначала видны неавторизованные запросы 401 для обнаружения OAuth, затем запрос с токеном. Успешный tools/list должен завершиться status 200 и upstreamStatus 200.
Функциональная проверка: в новом чате выберите рабочий плагин и отправьте «Покажи только папки верхнего уровня моего хранилища Obsidian. Ничего не изменяй». В журнале должен появиться tools/call с 200. Не используйте для первого теста удаление, запись или выполнение команд.
Выполнено в этой сессии: 10 тестов JWT и конфигурации; локальные MCP initialize, SSE, Session ID, tools/list и DELETE; проверка реальных сохранённых Windows учётных данных; публичный 401; OAuth вход ChatGPT; tools/list и tools/call с 200.
Проверка перезагрузки: сохраните работу, перезагрузите ПК в удобное время, войдите тем же пользователем, дождитесь Obsidian и Sync, повторите запрос из нового чата. Эту проверку пользователь должен выполнить отдельно; в ходе настройки перезагрузку не делали.
Проверка длительной работы: после истечения access token повторите безопасный запрос. Если требуется новый вход, проверьте offline_access, Allow Offline Access и Refresh Token. Фактическое обновление токена в длительной сессии пока не подтверждено.

Исправленная ошибка PowerShell
Симптом: Authentication succeeded, action discovery failed. В журнале запрос имел hasAuthorization true, rpc initialize или другой MCP метод, status 400 и не содержал upstreamStatus. Это означало, что проверка JWT уже пройдена, а обращение к Obsidian ещё не завершилось.
Причина установлена воспроизводимым тестом Windows PowerShell 5.1. Значение Get-Content -Raw при вложении в хеш таблицу и ConvertTo-Json могло сериализоваться как объект со свойствами value, PSPath, PSParentPath и прочими. HTTPS клиент Node ожидал строку PEM сертификата.
Исправление в Run.ps1: читать сертификат через [System.IO.File]::ReadAllText(...), что возвращает обычную строку. В start.mjs временно поддержан старый supervisor, извлекающий строку из ca.value. При новом запуске Run.ps1 передаёт уже правильный тип.
Дополнительно proxy.mjs проверяет тип API ключа и сертификата и разбирает CA через X509Certificate при старте. Невалидная конфигурация теперь останавливает запуск до публикации туннеля.
После исправления процесс прокси был точечно перезапущен. Тест тем же способом передачи через stdin и с сохранёнными DPAPI данными вернул initialize HTTP 200. Повторное подключение аккаунта в ChatGPT привело к tools/list 200 и реальному tools/call 200.
Это была ошибка подготовленного локального скрипта. Она не требовала смены пароля пользователя, ослабления OAuth, отключения TLS проверки или открытия Obsidian API без авторизации.

Диагностика других проблем
401 до OAuth входа — ожидаемый запрос авторизации. Постоянный 401 после входа — проверьте authError в requests.log: OWNER_MISMATCH означает другой пользователь, CLIENT_MISMATCH — другое приложение, SCOPE_MISSING — не выдан obsidian:mcp, ERR_JWT_EXPIRED — истёкший токен.
ERR_JWT_CLAIM_VALIDATION_FAILED — сверьте claim в журнале. Для aud сравните API Identifier и resource посимвольно, включая /mcp/ и слеш. Для iss сравните полный домен Auth0. Не выводите полный токен в журнал для диагностики.
502 или ошибка сертификата — проверьте, работает ли Obsidian, не изменился ли API ключ или CA, правильно ли выбран vault и доступен ли 127.0.0.1:27124. При регенерации ключа или сертификата повторно импортируйте данные установщиком.
ChatGPT показывает аккаунт, но не инструменты — проверьте факт tools/list. Отсутствие новых запросов означает, что попытка не дошла до прокси. Повторно подключите аккаунт или обновите метаданные там, где интерфейс предлагает Refresh. Не путайте это с загрузкой ZIP версии плагина.
Server not initialized — для старого stateful MCP нужно сначала initialize, затем notifications/initialized и сохранение Mcp-Session-Id. Простой curl GET с ключом не заменяет полный MCP handshake.
После сна нет доступа — разбудите ПК, проверьте сеть, Obsidian и задачу. После выхода из Windows требуется новый вход. Если перезапуски идут каждые 30 секунд, изучите status.log и проверьте порт, пути программ и конфигурацию ngrok.
429 — сработал локальный лимит или квоты провайдера. Сократите параллельные запросы, проверьте Usage ngrok. Долгие SSE соединения могут закрываться: в прокси есть idle timeout 3 минуты и ограничение отдельного соединения 1 час; клиент должен переподключаться.

Ежедневная работа и обновление
Рабочее подключение этой сессии называется obsidian-test. Можно оставить это имя. Старое неработающее obsidian удаляйте из ChatGPT только после проверки рабочего; удаление плагина в ChatGPT не равно удалению приложения или пользователя Auth0.
Перед запросом изменений с iPhone дождитесь Sync на Windows. Прокси не запускает синхронизацию по команде и не обещает мгновенную консистентность между устройствами.
Для чтения указывайте точную заметку или папку. Для изменений описывайте ожидаемый результат и просите подтверждение перед удалением. Инструменты vault_write, vault_delete и command_execute способны менять данные; доступ через OAuth сам по себе не делает их безопасными для любого запроса.
Обновления Node.js, ngrok и плагина Obsidian выполняйте контролируемо. После изменения протокола или tool schemas повторно проверьте discovery и безопасный tools/call. Прокси передаёт протокол существующего плагина, а не преобразует автоматически любую будущую версию MCP.
Проверенные ограничения: произвольные REST адреса и localhost ссылки загрузки и событий не публикуются. Большие тела запросов ограничены 2 МБ. Корректность всех двадцати инструментов, запись и бинарная загрузка отдельно не тестировались.
Для резервной копии сохраняйте исходники, package-lock.json и публичный config.json в защищённое место. Секреты и данные vault резервируйте по отдельной политике. Не прикладывайте secrets.dpapi.json к публичной инструкции.

Остановка отзыв доступа и перенос
Временная остановка: в Планировщике отключите ObsidianMcpProxy и завершите задачу. Проверьте, закрылись ли именно её node и ngrok. При принудительном завершении задачи Windows дочерние процессы могут остаться, поэтому одной кнопки Завершить недостаточно для доказанного отзыва доступа.
Проверка после остановки: публичный /mcp/ не должен давать успешный доступ к инструментам. Не завершайте все процессы node.exe или ngrok.exe: сначала сопоставьте процесс с путём start.mjs и параметрами данного туннеля.
Быстрый отзыв локального доступа: очистите allowedSubject в config.json и перезапустите именно прокси; валидация запретит его запуск. Дополнительно отключите аккаунт в ChatGPT и отзовите grant в Auth0. Уже выданный JWT обычно действует до exp, поэтому один отзыв refresh token не равен мгновенной блокировке на resource server.
Ротация ключа Obsidian: создайте новый ключ в плагине, повторно импортируйте его Install.ps1 и перезапустите связку. Ротация Authtoken: замените его в ngrok и запустите установку со скрытым вводом нового значения. Ротация Client Secret: замените его в Auth0 и защищённых настройках ChatGPT.
Перенос на другой компьютер: установите программы, скопируйте исходники, восстановите зависимости, укажите пути нового vault и Obsidian, заново сохраните секреты под нужным пользователем Windows и зарегистрируйте задачу. Не рассчитывайте на переносимость старого DPAPI файла.
При смене публичного домена согласованно измените publicOrigin, audience, Auth0 API Identifier, URL MCP в ChatGPT и настройки туннеля. После этого нужен новый вход и повторная проверка инструментов.

Техническое приложение и восстановление кода
Ниже приведены исходники рабочего комплекта на момент завершения настройки. Реальные идентификаторы и личные пути заменены шаблонами. Замените их перед запуском; секреты в исходный код не вставляйте.
Создайте отдельную папку и сохраните блоки в файлы с указанными именами. Страницы одного файла соединяйте подряд. Переносы очень длинных строк в печати являются только отображением; при копировании проверьте синтаксис.
Предпочтительный способ восстановления зависимостей из существующего комплекта — npm ci --ignore-scripts с его package-lock.json. Если восстанавливаете только по этому документу, выполните npm install --ignore-scripts: package.json закрепляет прямую зависимость jose версии 6.2.12 и создаёт новый lock файл.
В Install.ps1 шаблон C:\Users\YOUR_WINDOWS_USER\Documents\YOUR_VAULT замените реальным путём хранилища. Путь к Obsidian тоже зависит от установки. Публичный config.json не содержит API ключей.
Постоянный запуск обеспечивается планировщиком и supervisor Run.ps1. Не запускайте параллельно второй экземпляр на том же порту. Перед изменением файлов сохраните копию и после изменения выполните проверки.

import http from 'node:http';

export function validateConfig(c) {
  const origin = new URL(c.publicOrigin);
  const issuer = new URL(c.issuer);
  if (origin.protocol !== 'https:' || origin.origin !== c.publicOrigin || origin.username || origin.password ||
      issuer.protocol !== 'https:' || issuer.username || issuer.password || issuer.search || issuer.hash ||
      !c.issuer.endsWith('/') || c.audience !== c.publicOrigin + '/mcp/' ||
      !c.allowedSubject || !c.clientId || c.scope !== 'obsidian:mcp' ||
      !Number.isInteger(c.port) || c.port < 1024 || c.port > 65535) {
    throw new Error('Complete config.json with the Auth0 user ID and application Client ID.');
  }
}

export function makeVerifier(c, keys = createRemoteJWKSet(new URL('.well-known/jwks.json', c.issuer), {
  timeoutDuration: 5000, cooldownDuration: 30000, cacheMaxAge: 600000
})) {
  return async token => {
    const {payload: p} = await jwtVerify(token, keys, {
      algorithms: ['RS256'], issuer: c.issuer, audience: c.audience,
      requiredClaims: ['exp', 'iat', 'sub', 'azp'], clockTolerance: 0
    });
    for (const [code, denied] of [
      ['OWNER_MISMATCH', p.sub !== c.allowedSubject],
      ['CLIENT_MISMATCH', p.azp !== c.clientId],
      ['SCOPE_MISSING', typeof p.scope !== 'string' || !p.scope.split(' ').includes(c.scope)]
    ]) if (denied) throw Object.assign(new Error('Denied'), {code});
    return p;
  };
}

  for await (const chunk of process.stdin) { input += chunk; if (input.length > 65536) throw new Error('Input limit'); }
